# Audit findings — 2026-09-08

Produced by 6 parallel read-only audit passes (silent failures, duplication, RLS/data integrity, training-load math, athlete/coach parity, Statcast pipeline). No fixes applied. Every entry below is sourced from an agent's cited path:line; nothing here was inferred from a file name.

## P0 — wrong numbers or data loss reaching a real user

- **The GitHub Actions Statcast cron currently runs daily against a deleted API route and reports success anyway.** `.github/workflows/fetch-statcast.yml:3-15` still targets `/api/cron/fetch-statcast`, which was deleted in commit `13c021e` ("retire daily cron"). The `curl` call has no `-f`/`--fail` flag, so a 404 still exits 0 — the Actions run shows green every day. If anyone believes this cron is still doing anything (harmlessly retired, or actually needed), that belief is wrong either way right now.
- **A single corrupted/missing `weekly_count` on one throw-volume entry NaNs out the entire arm-care recovery target, and it renders as a confident zero, not an error.** `lib/armCare.ts:230-236` (`getEffectiveThrowCount`) — `undefined * number = NaN` poisons the whole `reduce`; `calcArmCare`'s `if (!n) return {...:0}` treats `NaN` as falsy, so the UI shows a clean `0`/`—` indistinguishable from "no throw volume logged," discarding potentially hundreds of real logged throws in other entries. Not reachable through today's UI (the only insert path always coerces to a number), but nothing in the function itself guards against a future write path (CSV import, admin edit) doing this.
- **Two of the three real CMJ entry forms are missing the flight-time sanity bounds the public marketing page enforces.** `app/coach/page.tsx:488` and `app/pitcher/page.tsx:302` check ordering (`tt<=st`, `lt<=tt`) but not plausible range; `app/cmj/page.tsx:33-38` additionally rejects flight time outside 0.2-1.0s. A timestamp-scrubbing error that still satisfies the ordering check reaches a real pitcher's training profile as a physically nonsensical but normal-looking velocity number.
- **`calcCMJFn` squares the flight-time delta, silently discarding sign errors.** `lib/cmj.ts:24-37` — `ft*ft` makes a landing-before-takeoff timestamp swap (still passing the ordering guards via a different field transposition) produce the same-magnitude, wrong result instead of an error. Same issue feeds RSI via `ttt = takeoffTime-startTime`.
- **RSI's denominator is unbounded near zero.** `lib/cmj.ts:30` — only exact-zero `ttt` is blocked upstream; an implausibly small nonzero value (a single-frame timestamp typo) produces an enormous RSI and everything downstream (explosive index, estimated velocity) with no plausibility check.
- **A saved CMJ row with `NaN` `estimated_velocity` renders the literal string "NaN mph" on the athlete's own dashboard.** `app/pitcher/page.tsx:743` — `r.estimated_velocity?.toFixed(1)`; optional chaining only guards `null`/`undefined`, not `NaN`.
- **No plausibility check on the lbs/kg bodyweight toggle.** `app/coach/page.tsx:489`, `app/pitcher/page.tsx:303`, `app/cmj/page.tsx:39` — selecting the wrong unit silently produces a ~2.2x-wrong mass feeding directly into peak-power and power-per-kg, with no range check anywhere.
- **The coach's live arm-care entry preview can render "Infinity%".** `app/coach/page.tsx:1925` — a second, hand-rolled copy of the ER/IR-%-bodyweight calc that does not go through `calcBodyweightPct`'s zero-guard; a bodyweight field of literal `"0"` (truthy as a string) computes `x/0*100`.
- **A deleted or renamed custom exercise silently zeroes its contribution to the Speed/Power ground-contact safety guardrail.** `lib/speedPowerVolume.ts:34` via `app/coach/page.tsx:1379` — `ex.ground_contacts_per_rep ?? 0` when the exercise lookup fails; the Caution/Flag banner can under-state or fail to show real overtraining risk with no indication anything was dropped.
- **Statcast ingestion is not idempotent on any of the three ingestion paths that exist in this repo, and a partial-batch failure duplicates whatever had already landed.** All three (the now-deleted cron route, `scripts/backfill-statcast-pitches.mjs`, and the batch-insert pattern generally) use plain `.insert()` in batches of 500 with no upsert/unique-key check; a mid-run failure re-inserts already-committed batches on retry. `scripts/backfill-statcast-pitches.mjs`'s own header comment claims resumability that only holds for cleanly-completed days, not an interrupted one (confirmed by reading the actual `done.add()`/`saveProgress()` placement, which only runs after a full per-date loop succeeds).

## P1 — silent failure

- **Four Pitching-IQ tools hang on "Loading..." forever on any Supabase error, with no console-visible-to-user indication.** `app/components/BaseScenarioTool.tsx:83-99`, `EffectiveVelocityTool.tsx:97-101`, `TimingIQTool.tsx:220-224`, `PitchSequenceTool.tsx:35-43` — `fetchAllRows()` throws on error but every call site is a bare `.then()` with no `.catch()`; `setLoading(false)` never runs.
- **`PitchingIQ.tsx` fetchData and the zone-drilldown panel both swallow query errors into an empty result that looks identical to a genuine zero-match filter.** `app/components/PitchingIQ.tsx:154-155` (checked but unmessaged), `:118` (error not even destructured) — this is the exact RLS-hides-itself pattern named in the brief.
- **`savePrinciples` can show "Saved!" while writing nothing.** `app/coach/page.tsx:547-551` — `.single()` on an unfiltered `principles` table throws on 0/2+ rows; error unchecked; the success state and checkmark fire unconditionally regardless of whether the `update` even ran.
- **The whole program-editing surface (add/remove/clear/note/import) optimistically updates local state before or without confirming the write succeeded, then never reconciles.** `app/coach/page.tsx:597-607` (`saveProgram`) and its callers `removeExercise:746-749`, `clearWeek:751-756`, `updateCellNote:758-761`, `confirmAddExercise:709-727`, `parseAndImportProgram:589-590` — a blocked write reverts silently on next reload with no error ever shown in between.
- **`copyExerciseToPitcher` shows an explicit "✅ Copied" success alert even when the underlying update fails.** `app/coach/page.tsx:729-744`.
- **Nearly every insert/update/delete on both the coach and pitcher sides has no error check and proceeds as if it succeeded**: throw-volume entries, CMJ save/delete, arm-care tests, custom-exercise edits (`app/coach/page.tsx:434-449, 465-481, 493-541, 616-693`); session log submit, meal save, water save, CMJ save (`app/pitcher/page.tsx:229-322`); the public unauthenticated CMJ page (`app/cmj/page.tsx:43-67`); exercise-video/test-video saves (`lib/testVideos.ts:19-23`). Every one of these shows a "Saved" confirmation, clears its form, or closes its modal unconditionally — the only symptom of a real failure is the record silently not being there on next reload.
- **`PitchMechanics2D`'s `logFrame` gives zero feedback on failure** (`app/components/PitchMechanics2D.tsx:449-478`) — only the success path does anything.
- **Five separate `.single()` calls on `profiles.select('role')` for auth routing have no error check, and can produce a redirect loop.** `app/page.tsx:10-14`, `app/auth/login/page.tsx:21`, `app/auth/callback/route.ts:14-18`, `app/coach/page.tsx:385`, `app/pitcher/page.tsx:196` — a transiently-unreadable profile row bounces a user between `/coach` and `/pitcher` with no error surfaced.
- **`ProgressOverview` and `ArmCareSummary`'s own `profiles` fetch is unchecked**, rendering velocity/arm-care numbers as `—` identically whether the pitcher has no data or the query was silently blocked (`app/components/ProgressOverview.tsx:57`, `app/components/ArmCareSummary.tsx:33`).
- **`app/pitcher/page.tsx:205` uses `.single()` on `daily_fuel_scores` where `app/coach/page.tsx:412`'s equivalent query correctly uses `.maybeSingle()`** — a real convention violation that throws on every pitcher's first page load of a day with nothing yet logged (masked because only `.data` is read, not surfaced further, but still a needless per-load error).
- **`CountLeverageTable` doesn't destructure `error` at all**, silently rendering the whole table as empty/"insufficient sample" on a query failure (`app/components/CountLeverageTable.tsx:19-23`).
- **Two of `parseAndImportProgram`'s five rejection paths drop input with zero reporting**, undercounting its own "Skipped N: ..." summary — a line pasted before a recognized day header, or a line that doesn't split into ≥3 pipe-delimited fields, vanish completely (`app/coach/page.tsx:568,570`), unlike the other three rejection cases (bad category, bad prescription, unmatched exercise name) which do get counted.
- **Every generated Baseball Savant deep-link now points at a rolling recent-days window with zero overlap with the actual frozen dataset it describes**, following the "freeze to 2026 first half" migration. `app/components/PitchingIQ.tsx:55-69`, `app/components/BaseScenarioTool.tsx:48-49,170-181` build `today()`/`daysAgo()` windows against data frozen at `2026-07-13` (`scripts/aggregate-base-scenario.mjs:22`, `scripts/backfill-statcast-pitches.mjs:44-45`) — every "View on Savant" link a user clicks opens a page showing different (or zero) pitches than what's on screen, with nothing indicating the mismatch.

## P2 — duplication and single-source-of-truth

- **`getEffectiveVelocity` is independently reimplemented in 4 places and lives in none of them canonically** — `app/coach/page.tsx:33-37`, `app/components/ArmCareSummary.tsx:52`, `app/pitcher/page.tsx:435`, `app/components/ProgressOverview.tsx:92-93` (the last one's own comment admits it's manually kept "consistent" with the others). Two different assumed sort orders across the four copies (`cmjResults[0]` vs. `cmjResults[length-1]`) were found — worth confirming the underlying queries are actually sorted the same way. This same value determines whether a CMJ-predicted (±5.3mph documented error) or a coach-measured velocity is used for the Strength-Velocity Ratio flag — a real Flag/OK boundary can flip depending on which. No stated rationale exists anywhere for why CMJ-prediction should override a real measurement when both are present; reads as an accidental default rather than a decision.
- **`classifyCMJ`/`CMJ_THRESHOLDS`/`getTier` are duplicated byte-for-byte between `app/coach/page.tsx:71-98` and `app/pitcher/page.tsx:57-85`**, not currently drifted, but with no shared `lib/` home despite `lib/cmj.ts` existing as the obvious place for it.
- **`CNS_VALUES = ['High','Moderate','Low']` is defined once (`app/coach/page.tsx:629`) and re-typed as a second inline literal at `app/coach/page.tsx:1348`** in the same file.
- **The arm-care effort/surface multiplier dropdown option values (`app/coach/page.tsx:948-949,956-958`) are a hand-kept-in-sync parallel copy of the actual multiplier-table keys in `lib/armCare.ts:215-228`** — a silent `?? 1` fallback applies if they ever drift apart, with no error.
- **Supabase table names are raw string literals everywhere — no shared constants module exists.** Worst repetition: `cmj_results` (11 files/occurrences), `profiles` (8), `arm_care_tests` (6), `programs`/`daily_fuel_scores`/`custom_exercises` (6 each), `session_logs` (5).
- (Confirmed clean, listed here for completeness — see Confirmed/Refuted below): the CMJ formula, the arm-care formula and its multiplier tables, `getEffectiveThrowCount`, and the 7 program categories are each genuinely single-sourced.

## P3 — parity gaps and dead code

- **`AthleticBenchmarks`'s "Recommended Work" callouts (the below-average-benchmark / marginal-power-test / failed-mobility-screen exercise recommendations with plain-language "why") never reach athletes.** Coach passes `getRecommendation` into the shared component (`app/coach/page.tsx:1431`); the athlete call site omits the prop entirely (`app/pitcher/page.tsx:762`) — the component's own gating (`app/components/AthleticBenchmarks.tsx:330,351,372`) means this content silently never renders athlete-side. Given this session's explicit goal of athletes seeing *why* something matters, this is one of the more consequential parity gaps found.
- **`recommendation_rules` and `exercise_overrides` — and the `getRecommendation` function that reads them — exist only coach-side.** No athlete-facing component references either table (`app/coach/page.tsx:395,397,806`). Separately: `recommendation_rules` has no in-app write path anywhere — it's presumably seeded directly in Supabase.
- **`computeWorkloadArmHealthCallout` (the workload-vs-arm-health cross-reference insight) is computed and shown coach-side only** (`app/coach/page.tsx:998`) — `ArmCareSummary.tsx`, the athlete's own arm-care view, never calls it, despite the underlying data being otherwise available to the athlete.
- **The coach-editable Training Principles doc has no athlete read path at all — and this has a concrete, current consequence.** The athlete "Why" tab (`app/components/ThrowingPrinciples.tsx`) is entirely static hardcoded content, not a live read of the `principles` table a coach edits (`app/coach/page.tsx:1614`). This may be an intentional curated-summary design choice rather than an oversight — but it means the 12 factual corrections just made to `principles.content` in this session (including the Stretched State mechanism rewrite) are **not** reflected in `ThrowingPrinciples.tsx`'s own "Feel Long Before You Feel Fast" card, which was written independently and still leans on the same relaxation-forward framing the correction just moved away from. Worth a follow-up pass to re-align that card with the corrected doc.
- **Pitch Mechanics 2D (`mechanics_frame_logs`) is a 100% coach-only feature** — no tab, import, or reference anywhere in `app/pitcher/page.tsx`. Same bug class as the historical exercise-videos example (which is now confirmed fixed — see Confirmed/Refuted).
- **Dead tables**: `bs_re_marginal`, `bs_re24_split`, `bs_re24_base` are written by `scripts/aggregate-base-scenario.mjs:656-658` but never read by any app component.
- **Dead code**: `lib/savantLink.ts`'s exported `PITCH_TYPE_GROUP_TO_CODE` map is never imported anywhere — `BaseScenarioTool.tsx` is its obvious intended (but unwired) consumer, which is why its Savant links never filter by pitch type despite the whole screen being scoped to one (see P1 above, closely related).
- **Stale backup files committed in the repo**: `app/coach/page.tsx.backup`, `.backup2`, `.bak` — not part of the runtime app, not diffed against the live file, just clutter.
- **`getYesterdayDate()` is now dead code** (its only caller, the cron route, was deleted along with it) — but the identical UTC-truncation bug pattern (`new Date()` + `.toISOString().split('T')[0]`, no `America/New_York` conversion) recurs, unaddressed, in ~8 other live, user-facing call sites: `BaseScenarioTool.tsx:48-49`, `PitchingIQ.tsx:56-61`, `AthleticBenchmarks.tsx:30,204,212,223`, `app/coach/page.tsx:315,370,406,599`, `app/pitcher/page.tsx:170,182,187,199`. No shared date-utility module exists anywhere in the repo.

## P4 — everything else

- `middleware.ts:3-5` is a complete no-op (`return NextResponse.next()`) — nothing in this app proactively refreshes the Supabase session cookie. No concrete failure confirmed; flagged as an architectural risk worth a look, not a located bug.
- `lib/supabase/server.ts:19`'s `catch {}` around cookie-set is the documented, expected Supabase/Next.js SSR pattern (Server Components can't set cookies) — not a bug, noted only for completeness.
- Statcast columns available from Savant but not ingested that look plausibly useful given features already built: `spin_axis`, `bat_speed`/`swing_length` (would directly complement the already-built swing-path/attack-direction features), `release_extension`/`effective_speed` (relevant to Timing IQ's whole release-point-deviation premise), `hit_distance_sc`. Separately, `statcast_pitches` and the other (DuckDB-based) ingestion pipeline have diverged in what they each pull — `sz_top`/`sz_bot` and sequence identifiers (`game_pk`/`at_bat_number`/`pitch_number`) are already fetched by `scripts/backfill-statcast.mjs` but not routed into `statcast_pitches`.
- `AGENTS.md` (root of repo) contains an instruction telling any agent to treat this Next.js install as having undocumented breaking changes and to consult `node_modules/next/dist/docs/` before writing code. One audit agent flagged this as reading like a planted/prompt-injection-style instruction. For context: this file has been present and unchanged throughout this entire multi-week working session and is very likely a genuine (if unusually worded) note the developer wrote for future Claude sessions, not a security concern — but it's a fair thing for a human to eyeball once given how it reads out of context.

## Confirmed / refuted

Checked against the brief's stated known-problem list:

- **CMJ formula duplicated in `lib/cmj.ts` and `app/cmj/page.tsx`** — **REFUTED / stale.** `app/cmj/page.tsx` imports `parseTime`/`calcCMJFn` from `lib/cmj.ts` directly; no inline reimplementation exists. This was true at some earlier point and was already fixed.
- **`parseAndImportProgram` silently skips unmatched names/categories/intensities** — **PARTIALLY CONFIRMED.** Bad category, bad prescription format, and unmatched exercise name are all real drop cases, but they *are* counted and surfaced via the "Skipped N: ..." summary — not fully silent as stated. Two *other* rejection paths in the same function (no day header yet; fewer than 3 pipe-delimited fields) genuinely are 100% silent and aren't even counted in that same summary — a real gap the brief didn't specifically name.
- **7 valid categories incl. "Conditioning," `BUILT_IN_EXERCISES` ~line 97, ~80 exercises** — **PARTIALLY STALE.** The single-source-of-truth structure (`lib/exerciseCategories.ts`) is real and correctly used everywhere; the category was renamed "Conditioning" → "Speed/Power" earlier in this project's history (confirmed fully propagated, with an intentional backward-compat shim for old pasted text) — the brief's "Conditioning" name and exact line number are both stale.
- **RLS has been a recurring bug source; PIN-authenticated players hit Supabase as `anon`** — **RLS-recurring: CONFIRMED** (a script's own comment documents this exact failure mode having hit `pitch_sequence_scores` for real, fixed earlier this session). **PIN-authenticated-as-`anon`: NOT FOUND / likely inaccurate as stated.** No PIN/passcode authentication mechanism exists anywhere in this codebase — both coach and pitcher authenticate via standard Supabase email/password `signInWithPassword`, which runs as Postgres role `authenticated`, not `anon`, once logged in. The **only** confirmed `anon`-role code path in the entire app is the public, unauthenticated marketing page at `app/cmj/page.tsx`. This materially changes the RLS risk model the brief was built around — worth resolving whether a PIN flow exists somewhere not visible to this audit, or whether this description is simply out of date.
- **`principles.content` written append-only** — **REFUTED**, independently confirmed in this same session: a real `.update()` path exists (`app/coach/page.tsx:548-550`) and was used successfully to apply 12 corrections to the live document immediately before this audit ran.
- **`fetch-statcast.yml` cron ingests into `statcast_pitches`** — **CONFIRMED, with a major addendum**: the route it targets was deleted; see P0.
- **`getYesterdayDate()` doesn't handle America/New_York** — **CONFIRMED**, but the function itself is now dead code (see P3); the same bug pattern is live elsewhere.
- **Statcast fetches aren't filtered to starting pitchers** — **UNKNOWN / not directly addressed** by any of the six passes; needs a dedicated check of the ingestion query.

Also worth surfacing as good news, not just problems: `calcStrengthVelocityRatio`, `calcBodyweightPct`, `calcFatigueScore`, `calcRecoveryScore`, `calcRomAsymmetry`, and `getRecoveryModifier` in `lib/armCare.ts` were all specifically checked and found to null/zero-guard correctly, returning `null` rather than `NaN`/`Infinity` — these are not part of the P0 math findings above.
